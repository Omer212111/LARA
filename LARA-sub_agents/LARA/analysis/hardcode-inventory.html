The rule we are measured against

Not allowed: hardcode any API calls into their agent's logic, e.g., login into all apps in the first hardcoded execution call and save its access tokens in a variable.
Allowed: tell the agent in the prompt to do so by itself · give generic hints inferred based on train or dev failures (not test sets).

That is two separate rules, and we break both. The line is: prompt text is allowed, code that calls APIs for the model is not — and anything learned from a test split is not allowed at all, whether it sits in a prompt or in code.

How this was measured

Two methods, because they answer different questions. Static coverage counts exactly; a benchmark run can only sample.

Static coverage. Three surfaces decide what they do purely from the task instruction string, so their reach is countable over all 732 tasks with no LLM and no run — analysis/hardcode_coverage.py.

Runtime trace. Records which surface actually fired, per task, with the official world.evaluate() verdict attached — analysis/hardcode_trace.py. It stays off unless LARA_HARDCODE_TRACE names an output file, so the traced code is the same code that runs the leaderboard.

The fact that makes Tier 4 replaceable.

204 of the 240 API names cited in specialist prompts appear literally in data/api_docs/standard/<app>.json — the same docs the api_docs app serves at runtime. The other 36 are our helper names, parameter names, or prose.

And the agent is already reading those docs: 152 runtime lookups across 20 of 20 tasks. The discovery path works today and carries real traffic, so moving the API listings out of the prompts has somewhere to land.

What is not re-derivable from docs is the strategy content — which field a task word maps to, pagination gotchas, ACTION versus VALUE. Most of that sits squarely inside "generic hints" and can stay, provided it came from train or dev.

The measurement that shapes the replacement work

The model never calls an app API directly.

Across 20 tasks the only direct apis.* call it wrote was apis.supervisor.complete_task — 20 times, once per task. Every single app API call went through call_api or fetch_all_pages.

So the helper layer is not a convenience the model routes around when it feels like it. It is the only path it uses. H5, H9 and H10 cannot simply be deleted — they have to be replaced by prompt instructions telling the model to do the same thing itself, which is exactly what the rule permits.

For completeness: the ledger helpers remember, recall and remember_entity fired on one task each, one call each, out of 20. No API calls inside them, so no compliance question — but they are carrying prompt weight for nothing, consistent with the 2.3% adoption already recorded in CLAUDE.md.

Replacement plan

The rule permits moving the same knowledge into the prompt — "it is okay to tell the agent in the prompt to do so by itself". Most of these are a move from code to text, not a loss of capability.

One distinction saves most of the pain.

The rule forbids hardcoding API calls. Two of our helpers hardcode a specific API — login_to_app calls apis.supervisor.show_account_passwords(), find_contact calls apis.phone.search_contacts. Those are what the rule describes.

call_api and fetch_all_pages hardcode no specific API at all. They are generic dispatchers that take the app and API name as arguments — getattr(getattr(apis, app), api) is not a hardcoded API call.

Under that reading H9 and H10 are fine and only H5 and H6 have to go. That is the difference between giving up 84 helper calls and giving up 155. Open a GitHub issue with the AppWorld organizers and ask before dismantling something that works — a two-day wait against days of rework.

H2·H3
Needs a replacement

Replace the Amazon patterns with a generic container rule

The insight underneath PATTERN A and B is not Amazon-specific: when a task says "all X in my <container>", the items are already in the container — do not search the catalog. That is the same rule already sitting in the Explorer prompt's AGGREGATION SCOPE section, which was derived from Spotify tasks in train.

Replace all three PATTERN blocks with one generic, Amazon-free scoping rule, and let the API names be discovered through api_docs at runtime.

H5
Hardest
must preservetoken caching

Move the login recipe into the prompt

Take the helper out of BOOTSTRAP_CODE and put the recipe itself in the prompt:

profile = apis.supervisor.show_profile()
creds   = apis.supervisor.show_account_passwords()
pw      = next(c['password'] for c in creds if c['account_name'] == 'venmo')
token   = apis.venmo.login(username=profile['email'], password=pw)['access_token']

What protects the quality is the caching. Today the token lives in the ledger and a repeat call is free. Without it the model re-logs in every step and burns ReAct budget. The fix is already documented in our own code (executor_helpers.py:31–35): the sandbox is a single long-lived shell per task, so a variable survives between blocks. Add that to the prompt — "log in once, keep it in venmo_token, the variable persists; do not log in again."

Same behaviour, model-authored. Costs about four extra lines per task instead of one helper call. Must be measured.

Protecting the quality

Per CLAUDE.md, run-to-run variance at n=20 is large — the same task has gone 8/8 and 3/8. A single run is directional, not proof. The protocol matters more than any individual change.

1

Build the quality gate before touching anything

Not test_normal — it is single-use and already spent. Use a fixed slice of about 40 tasks drawn from train and dev, stratified by app count. Run it once on current code; that is the baseline. Roughly 45–50 minutes per run.

2

Change one thing, re-run the same task IDs

Never resample. For every task that flips, check the log for whether the code path you changed was even exercised — CLAUDE.md records a "regression" that turned out to be attempt-1 variance on untouched code.

3

Order of work

H1, H4 and H6 first — free, no measurement needed. Then the base.py:426 bug and the ledger. Then H11. Then H5, the risky one, with the recipe in the prompt. Leave H9 and H10 alone until the organizers answer.

What cannot be promised

One place where quality probably does drop: Amazon tasks in test_challenge. 52% of that split touches Amazon, and some of the current capability there was bought with patterns derived from that same split.

But test_challenge has never been run, so there is no baseline to lose. That is an unmeasured unknown, not a regression. The only real baseline is 54.8 on test_normal — and every Tier 1 surface is measured at zero matches there.
